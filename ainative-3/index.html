AI-NATIVE FIELD NOTES · 03 · INTERNAL SHARING

执行成本降低后
AI-native 团队

如何重构上下文、行动边界与结果责任

辛海洋2026年8月31日可可乐博
这是 AI-native 系列第三篇。第一篇解释 Agent 为什么开始能接下一件事，第二篇讨论组织与产品底座应转向什么；这一篇继续分析产品与研发如何把执行能力转化为责任明确的工作系统。分享综合 Uber Engineering 的 Software Factory 案例、Ashwin Gopinath 的 Company Memory 系列、三篇关于 Agent Loop 与任务图的实践文章，以及 Joway 关于 AI Coding 责任的实践论述。五级演进、六类责任和实施计划属于结合可可乐博现阶段实践形成的分析建议。

01 · CENTRAL JUDGMENT

AI Native 改造的对象
是工作系统

任务需要从个人会话转化为具有上下文、权限、验收、记录与责任的工作系统。模型使用率和 Agent 数量只能说明采用程度，不能说明这种能力已经成为组织的稳定属性。

可理解可执行可验证可学习
本页给出全文判断：AI Native 改造的对象是工作系统，而不是单个模型或岗位。其成立条件是同类工作可以在关键成员缺席时复现，结果依据可说明，失败后可恢复，运行结果能够更新后续工作。

02 · THE SHIFTING BOTTLENECK

执行成本下降后，
上下文与责任成为主要约束

生成、检索和工具调用快速扩展后，团队差异不会消失，而会转移到任务定义、上下文、验证与结果责任。

该关系图是分析模型，不是实测曲线。其含义是：随着 Agent 执行范围扩大，组织需要处理更多授权、冲突、审批和结果责任。Joway《尽职编程》提出，即使工程师使用相近的模型与工具，工作结果仍取决于负责人是否理解关键选择并完成相称的验证；本文据此将团队差异解释为任务定义、上下文、验证和结果责任的差异。这一判断不表示已有数据证明 AI Coding 扩大了个体产出方差。单次任务成本下降，也不保证整体协调成本同步下降。
01WHY AI NATIVE

PART ONE · ONE ORGANIZATIONAL PROBLEM

行动能力增长快于
组织控制能力

Uber 讨论如何规模化执行；Company Memory 讨论行动依据如何保存。两组材料共同指向上下文、行动边界与结果学习的缺口。

第一部分不分别复述两组材料，而是用它们解释同一组织问题。Uber 展示行动能力如何通过任务分层、Benchmark 和托管环境扩大；Company Memory 指出决策原因、承诺、例外与结果没有随执行能力同步进入系统。二者之间的差距构成本次分享的分析起点。

01.1 · UBER SOFTWARE FACTORY

Uber 展示了
Agent 工厂的运行规模

从 2026 年 2 月至 8 月，Uber 自述 Agent 产品周活用户增长 7 倍，请求增长 9.4 倍；总 AI 支出自 4 月以来“相对稳定”。

企业自述 · 未公开绝对成本与完整归因口径

来源：Uber Engineering, Running a Software Factory Efficiently at Uber Scale, 2026-08-27。文章还披露超过 70% PR 被归因于本地或云端 Agent、3,600 多个 Skills、每日 30,000 多次 Skill 执行。这些数字不能改写为“70% 代码由 AI 完成”，也不是组织生产率的外部审计证明。

01.2 · CONTROL BEFORE SCALE

Agent 工厂的控制力来自
任务分层与真实评测

托管程度由任务边界、可观察性与恢复能力决定；模型选择由真实任务评测决定。

本页合并 Uber 的四层工作形态与 Benchmark 方法。Raw Session、带 Skill 的会话、通用 Agent 和专用 Agent 的差异不只是模型能力，而是任务边界、运行环境和结果责任的控制程度。uReview 进一步说明，模型和工作流应依据真实 PR 的 precision、recall、延迟、超时、人工复核与单位结果成本选择。图中的 Pareto 曲线为方法示意，不对应 Uber 的具体点位。

01.3 · ORGANIZATIONAL MEMORY

组织记忆需要保存
事实、推理与行动

事实记忆

发生了什么，证据在哪里，由谁负责，何时变化。

推理记忆

为什么这样决定，哪些方案被否决，什么假设仍未关闭。

行动记忆

什么条件触发工作，真实路径如何运行，结果是否符合预期。

这一分类来自 Company Memory 系列，属于具有商业产品立场的架构判断，不是组织效果的独立验证。

本页合并 Context Ceiling 与三类记忆。代码、PRD 和流程能够保存显式产物，却经常省略被否决方案、客户承诺、合规约束和历史失败。Ashwin Gopinath 将组织记忆区分为事实、互动与推理、行动三类。作者同时是 Sentra 创业者，因此该分类应作为可检验的架构判断，而不是普遍效果结论。

01.4 · STATE AND ACTION BOUNDARY

共享状态既要支持行动
也要限制行动

技术上可以调用工具，不代表组织上已经授权；行动边界必须来自可检查的共享状态。

本页合并共享状态与 Action Memory。多个工具不应分别形成互相漂移的局部真相；底层状态需要由组织控制来源、版本、权限和关系。状态进入行动前，还要经过证据、风险、授权和回退检查。系统必须允许执行，也必须允许等待、拒绝、升级和回滚，并把结果写回。

01.5 · OPERATING FOUNDATION

Context、Harness、Loop
构成共同基础

Context

事实、决策原因、约束、承诺和历史状态。

Harness

工具、权限、任务图、预算、验证门与停止条件。

Loop

执行、验证、人工修正、结果写回、版本更新与撤销。

该框架来自可可乐博既有实践，并由本次材料进一步支持。Context 回答系统基于什么理解任务；Harness 回答工具、权限、任务图、预算与验证门如何组织行动；Loop 回答一次执行怎样被检查、修正并进入下一次工作。Graph 不是第四个基础层，而是 Harness 中组织节点状态、真实依赖、并行、汇聚和失败边界的执行拓扑。运行 State 回答这一轮执行到了哪里，组织 Context 回答行动基于哪些事实、决策、约束与历史，二者不能互相替代。

01.6 · FIVE CAPABILITY LEVELS

AI Native 转型经历
五级能力演进

这是一种能力诊断框架，而非线性排名。晋级依据是复用、治理、共享状态与结果学习是否成立。

五级演进属于本文综合分析：L1 是个人工具使用；L2 将有效方法固化为可复用工作流；L3 在受治理的 Harness 中托管执行；L4 由产品、内容和研发读取同一共享状态；L5 依据真实结果更新 Context、Benchmark、Skill 与 Workflow。团队可能在不同工作流上处于不同级别，不能以统一标签替代逐项评估。
02TEAM REDESIGN

PART TWO · SHARED WORK STATE

产品、内容与研发
需要同一条状态链

产品保存判断依据，内容保存来源与专业审查，研发保存约束与验证；三条链必须在交付结果处汇合。

第二部分把团队改造扩展到产品、内容和研发三类专业工作。三者不需要使用同一款工具，但必须共享目标、证据边界、版本、验收标准和结果状态。产品负责判断链，内容负责来源、权利、专业审查与资产版本，研发负责执行环境、验证与恢复。各团队的候选输出进入共享状态前仍需具名确认。

02.1 · PRODUCT JUDGMENT STATE

产品工作需要形成
可追溯判断链

PRD 是某一时点的呈现；底层判断状态需要保留来源、异议、责任和失效条件。

该状态链属于本文建议。它将产品材料从静态文档转为可追溯判断：原始证据与产品解释分开，异议和反例不被新版本覆盖，发布结果能够更新原始假设。AI 可以生成候选状态，但具名负责人确认后才能成为共享状态。

02.2 · PRODUCT TEAM

产品团队的约束转向
证据与决策质量

证据分层

区分来源事实、产品解释、假设和已批准决策。

保存分歧

暴露销售、产品、研发和支持之间的状态冲突。

具名批准

候选承诺、Owner 和优先级由负责人确认后写入。

结果写回

发布后根据观察窗口判断假设是否成立或需要撤回。

产品系统可以准备证据和候选方案，但不能替代对用户承诺、优先级和结果的责任。

本页为实施建议。产品团队可以优先改造访谈与反馈证据化、PRD first-pass review、实验结果整理和冲突提示。涉及路线图承诺、定价、敏感用户评价和公开发布的决定，仍需要明确的人类批准。

02.3 · ENGINEERING EXECUTION

研发工作需要形成
可验证执行链

01目标02约束03方案 04变更05测试06固定证据 07批准08发布09结果写回

异常路径、人工修正与生产结果返回 Failure / Outcome Context。

代码 diff 只说明发生了变更；每项 AI 生成变更都应有具名工程负责人，能够说明依据、设计、副作用、验证证据与回退条件。

该执行链属于本文建议。固定 SHA 表示验收对象需要可复现；测试证据需要区分本地、CI、Preview 和生产环境。具名工程负责人需要理解关键设计、依赖、潜在副作用与验证证据，并记录接受或拒绝 Review 意见的依据。架构图和设计说明可以辅助理解，但不能替代对关键代码、测试与运行结果的检查。合并后还要写回能力、约束、风险与技术债的变化，避免异常路径只停留在聊天记录。来源补充：Joway《尽职编程：AI Coding 时代的个体产出差异的来源》；该文属于实践观点，不构成效果评测。

研发团队不只实现 Agent 节点，还要定义状态契约、依赖拓扑、失败边界与停止预算。

02.5 · CONTENT TEAM

内容团队需要形成
可追溯资产与复用结果

来源与权利

记录来源、授权、适用对象、版本、有效期与引用范围。

结构化资产

把概念、活动、素材与评价标准拆成可检索、可组合的版本化对象。

专业审查

事实、教学、语言、版权与安全检查由具名负责人确认后发布。

结果写回

将采用、修改、拒绝、纠错、复用与实际使用证据写回资产状态。

内容产量只能反映生成规模；可追溯、可审查、可复用且能根据结果修订，才构成组织能力。

本页为针对可可乐博内容团队的实施建议，不是对外部来源的效果归因。AI 系统可以协助检索、拆分、标注和生成候选内容，但未经核验的来源、授权不明素材、专业判断和对外发布不能自动进入公司事实。建议从一类高频内容资产建立版本、审查记录、复用关系与使用反馈。

六类责任并非六个岗位；小团队可以兼任，但每项责任必须具名、可检查并可追溯。

六类责任描述团队成员工作的重心，而不是新增六个岗位。Context 对应目标定义与证据判断；Harness 对应委托设计与例外处理；Loop 对应结果责任与学习演进。委托设计发生在执行之前，负责状态契约、节点、真实依赖、工具、权限、预算、验证门和停止条件；例外处理发生在运行期间，负责冲突、低置信、高风险、失败恢复与人工接管；结果责任要求具名负责人理解并说明关键选择，完成验收、发布、观察、修订或撤回；学习与演进把已确认的失败、人工修正和业务结果写回 Context、评估集与工作流版本。Joway 所称“尽职编程”在本框架中是六类责任的综合表现，不单独构成第七类责任。六类责任是本文综合判断，不是外部来源提出的统一岗位模型。
03TRANSFORMATION PATH

PART THREE · EVIDENCE-GATED AUTHORITY

权限扩大必须通过
结果证据门槛

自动化权限不是按时间自然增加。只有结果可靠、失败可恢复且人类责任容量足够时，工作流才适合进入下一层级。

第三部分以权限晋级条件为中心。该公式是实施判断，不是数学模型。扩大 Agent 权限前，需要同时观察结果可靠性、失败后的恢复能力和人类审批与升级容量；具体行动还要按影响范围与可逆性分流。尽职不等于无限审查：验证深度应随影响范围、不可逆性、数据与权限风险、系统耦合度和变化速度增加。高风险行动不应只依赖提示词要求模型询问，而应在系统上保持不可达，直到批准、证据与版本条件同时成立。模型自报置信度只能作为次级信号。该原则与 OpenAI Agent 指南对工具风险、可逆性和人工监督的建议一致。

03.1 · MEASUREMENT SYSTEM

衡量方式必须覆盖
结果、监督负担与风险

结果价值

验收通过 · 业务结果 · 质量缺陷 · 结果写回

单位成本

模型 + 工具 + 人工复核 + 返工 ÷ 被接受成果

运行健康

失败单元 · 重试上限 · Gate 阻断 · 轨迹完整

治理风险

越权 · 人工介入 · 升级时延 · 回退成功

Agent 数量、Token 总量和 AI 参与率是采用指标；只有与基线、质量和风险共同解释，才能支持晋级。

衡量体系属于实施建议。北极星指标将可接受结果与人类监督负担同时纳入；单位被接受成果成本还需要计入模型、工具、人工复核和返工。运行健康用于判断失败是否被正确阻断、是否只退回失败单元、重试与升级是否在预算内、轨迹能否解释结果。Review 的有效性应结合有效问题闭环、闸门后缺陷逃逸、无证据覆盖、重复问题和修复时延判断；评论数量、轮次或耗时不能单独证明审查尽职。Gate 阻断率也不能单独解释：阻断率为零可能表示上游质量高，也可能表示检查无效，必须结合错误逃逸和人工抽检。产品、研发和内容仍需建立各自基线，不宜用统一分数横向排名。

03.2 · DURABLE CAPABILITY PATH

可持续转型依赖
五类可迁移资产

模型可以替换；组织自有的上下文、评估、工作流、治理和结果资产必须持续积累并可导出。

本页回答可持续能力建设问题，并与下一页时间路线区分。每一条真实任务都应留下五类可迁移资产：可追溯 Context、真实任务评估集、版本化 Skill 与 Workflow、权限和恢复记录、业务结果与人工修正。Review 异议、负责人回应、测试证据与最终决定也应进入相应资产：被否决方案与理由进入 Context，反例与逃逸缺陷进入评估资产，Reviewer 配置与验证门进入工作流资产，批准、豁免和回退进入治理资产，返工与用户影响进入结果资产。两条返回路径需要区分：短纠错边修正本轮失败单元；长学习边把具名确认后的失败、修正和结果转化为下一轮 Context、评估集和工作流约束。Graph Spec、State Schema、Checkpoint 和失败轨迹分别进入工作流、治理与结果资产，不新增第六类资产。

03.3 · 12-MONTH ROADMAP

改造计划从共享语言推进到
可迁移运行

路线图属于实施建议。M0 定义共同状态语言和基线；M1 建立只读可追溯链；M2 允许具名确认后的状态写回；M3 对触发条件影子告警，并让独立 Review Agent 以只读方式运行，测量有效发现、误报、漏报和人工处理成本；M4 只将已经验证的高风险规则设为强制门，并运行一条受控 Action Loop，同时要求 Graph Spec 与 State Schema 完成评审、每条 edge 有明确跨节点数据、失败单元可单独恢复、宽度与重试等预算实际生效；M5 检验 Context、Benchmark 和运行记录能否跨模型或 Harness 迁移。

03.4 · FIRST VERTICAL SLICE

首个试点应打通一条
真实纵向链路

先证明状态链可检查、可纠正、可恢复和可复现，再讨论扩大 Agent 数量与权限。

建议选择一条正在发生、风险可控的真实功能，不建设全公司大图谱。试点需要同时覆盖产品证据、内容资产、工作契约、研发执行、固定 SHA 验收、人工发布批准和结果写回。工程负责人还需要能够依据实现说明解释关键设计、兼容性、副作用、未覆盖情形、回退方式和结果指标；说明文档用于支持审查，不替代真实验收。由此检验 Context、Harness、Loop 是否形成有效连接。

SUMMARY · THREE DECISIONS

本次分享需要形成
三个组织决策

01选择一条真实纵向链路

选择正在发生、风险可控且结果可观察的功能，不建设全公司知识图谱。

02定义共同工作契约

明确证据、约束、验收、Outcome Owner、Approver、观察窗口和回退条件。

03建立基线与晋级门槛

测量通过验收的结果、人工监督时间、错误与恢复；达到门槛后再扩大权限。

如果这三项不能明确，增加 Agent 数量只能说明采用扩大，不能证明组织能力已经形成。

总结不再重复概念，而是要求形成三个决策。第一，确定一条真实纵向链路。第二，为这条链路定义共同工作契约和具名责任。第三，建立结果、监督、错误与恢复基线，并据此设置权限晋级门槛。下一页提供四个长期检验问题。
