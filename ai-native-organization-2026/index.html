AI NATIVE ORGANIZATION · INTERNAL SHARING

从 AI 提效到
AI Native 组织

执行系统、组织记忆与责任机制的共同改造

辛海洋2026年8月31日可可乐博
本次分享综合两组公开材料：Uber Engineering 的 Software Factory 案例说明 Agent 如何进入生产系统；Ashwin Gopinath 的 Company Memory 系列说明组织为何需要保存决策原因、承诺、例外与结果。后续框架和实施计划属于结合可可乐博现阶段实践形成的分析建议。

01 · CENTRAL JUDGMENT

AI Native 转型改变的，
是组织运行工作的方式

任务需要从个人会话转化为具有上下文、权限、验收、记录与责任的工作系统。模型使用率和 Agent 数量只能说明采用程度，不能证明组织能力已经形成。

可理解可执行可验证可学习
本页给出全文判断。AI Native 不是模型接入的同义词。组织转型成立的条件，是同类工作可以在关键成员缺席时复现，可以说明结果依据，可以在失败后恢复，并能把运行结果转化为后续能力。

02 · THE SHIFTING BOTTLENECK

执行成本下降后，
上下文与责任成为主要约束

生成、检索和工具调用可以扩展得很快；决策原因、权限边界、例外判断和结果责任仍需要组织明确承担。

该关系图是分析模型，不是实测曲线。其含义是：随着 Agent 执行范围扩大，组织需要处理更多授权、冲突、审批和结果责任。单次任务成本下降，并不保证整体协调成本同步下降。

03 · UBER SOFTWARE FACTORY

Uber 展示了
Agent 工厂的运行规模

从 2026 年 2 月至 8 月，Uber 自述 Agent 产品周活用户增长 7 倍，请求增长 9.4 倍；总 AI 支出自 4 月以来“相对稳定”。

企业自述 · 未公开绝对成本与完整归因口径

来源：Uber Engineering, Running a Software Factory Efficiently at Uber Scale, 2026-08-27。文章还披露超过 70% PR 被归因于本地或云端 Agent、3,600 多个 Skills、每日 30,000 多次 Skill 执行。这些数字不能改写为“70% 代码由 AI 完成”，也不是组织生产率的外部审计证明。

04 · FOUR OPERATING LAYERS

成熟度提升来自
任务边界与控制权

不是所有任务都需要进入最高层级。只有边界稳定、结果可观察、失败可恢复且责任明确的任务，才适合提高托管程度。

来源：Uber 文章 Figure 3。四个层级分别是 Raw Sessions、Sessions with Skills、General Agents、Specialized Agents。这里保留其工作形态，但将“成熟度”解释为组织对任务边界、运行环境和结果责任的控制程度。

05 · BENCHMARK BEFORE ROUTING

真实任务评测决定
模型与工作流选择

从历史工作建立 Benchmark，同时比较正确性、漏报与误报、延迟、超时、人工复核和结果单位成本。模型是可替换变量，评测集和验收责任属于组织。

质量可靠性人类负担成本
来源：Uber Software Factory 与 uReview 文章。uReview 使用带已知 Bug 的真实 PR，评估 precision、recall、F1、cost / review、延迟、超时和噪音。本页散点为方法示意，不对应 Uber Figure 5 的具体点位。

06 · THE CONTEXT CEILING

代码和文档不能完整保存
组织推理

Agent 可以读取实现，却未必知道合规约束、客户承诺、被否决方案和历史失败为何决定了当前路径。

来源：Ashwin Gopinath 关于 AI Coding Limitations 的公开论述，以及 Company Brain 系列。作者同时是 Sentra 创业者，其架构判断具有产品立场。本页采用冰山图表达“可见产物与组织推理之间的差异”，不是对任何企业的实测比例。

07 · THREE MEMORIES

组织记忆包含
事实、推理与行动

事实

发生了什么，证据在哪里，由谁负责，何时变化。

推理

为什么这样决定，存在什么异议，哪些假设未关闭。

行动

何时启动、等待或升级，真实路径与结果是什么。

来源：Ashwin Gopinath, Company Brain、Interaction Memory、Action Memory。三层不是三个彼此独立的产品，而应被视为同一组织状态的不同内容。分类本身仍需结合具体行业和工作对象验证。

08 · MEMORY AS SHARED STATE

共享状态避免每个工具
形成局部真相

同一证据可以被不同角色解释，但底层来源、版本和权限不应复制成相互漂移的多套事实。

来源：Ashwin Gopinath, Memory Is State, Not a Service。作者主张公司记忆应可检查、纠正、版本化、授权和迁移。我们据此建议使用“同一共享状态、多个具名视角”，而不是立即设计一张全公司万能 schema。

09 · ACTION MEMORY

可靠的 Agent 必须能够
有意识地不行动

技术上可调用工具，不代表组织上已经授权。流程契约应同时定义执行、等待、拒绝、升级和回滚。

来源：Ashwin Gopinath, Action Memory。其核心主张是系统需要记住何时唤醒工作、实际怎样执行，以及结果如何。我们将其转译为工作流契约中的 wait、abstain、escalate 和 rollback。

10 · OPERATING FOUNDATION

Context、Harness、Loop
构成共同基础

Context

事实、决策原因、约束、承诺和历史状态。

Harness

工具、身份、权限、预算、测试、审批和停止条件。

Loop

执行、验证、人工修正、结果写回、版本更新与撤销。

该框架来自可可乐博既有实践，并由前述两组材料进一步支持。Context 回答系统基于什么理解任务；Harness 回答它如何行动并受约束；Loop 回答一次执行怎样进入下一次工作。三者共同服务于可验证结果，而不是各自成为独立平台目标。

11 · FIVE CAPABILITY STAGES

AI Native 转型经历
五个能力阶段

阶段不等于组织规模。只有真实任务在明确责任下通过验收，才能从上一阶段晋级。

五阶段模型属于本文综合推断：个人工具使用、工作流沉淀、Agent 托管执行、共享组织状态、基于结果持续进化。其目的不是制造成熟度排名，而是帮助团队区分当前缺口位于复用、执行治理、共享状态还是学习机制。

12 · PRODUCT JUDGMENT STATE

产品工作需要形成
可追溯判断链

PRD 是某一时点的呈现；底层判断状态需要保留来源、异议、责任和失效条件。

该状态链属于本文建议。它将产品材料从静态文档转为可追溯判断：原始证据与产品解释分开，异议和反例不被新版本覆盖，发布结果能够更新原始假设。AI 可以生成候选状态，但具名负责人确认后才能成为共享状态。

13 · PRODUCT TEAM

产品团队的约束转向
证据与决策质量

证据分层

区分来源事实、产品解释、假设和已批准决策。

保存分歧

暴露销售、产品、研发和支持之间的状态冲突。

具名批准

候选承诺、Owner 和优先级由负责人确认后写入。

结果写回

发布后根据观察窗口判断假设是否成立或需要撤回。

产品系统可以准备证据和候选方案，但不能替代对用户承诺、优先级和结果的责任。

本页为实施建议。产品团队可以优先改造访谈与反馈证据化、PRD first-pass review、实验结果整理和冲突提示。涉及路线图承诺、定价、敏感用户评价和公开发布的决定，仍需要明确的人类批准。

14 · ENGINEERING EXECUTION STATE

研发工作需要形成
可验证执行链

代码 diff 只说明发生了变更；执行状态还要说明依据、环境、验收人、回退和实际结果。

该执行链属于本文建议。固定 SHA 表示验收对象需要可复现；测试证据需要区分本地、CI、Preview 和生产环境。合并后写回能力、约束、风险与技术债的变化，避免异常路径只停留在聊天记录。

15 · ENGINEERING TEAM

研发团队的约束转向
系统设计与验证

Decision Context

读取架构原因、被否决方案、兼容性和合规边界。

避免技术上正确、组织上错误
Failure Context

保存历史事故、失败迁移、人工恢复和适用范围。

减少重复调查与重复事故
Evidence Gate

区分单测、浏览器、数据库、Preview 与生产证据。

测试通过不等于结果成立
Recovery Contract

定义停止重试、请求审批、回滚与人工接管。

自动执行不取消恢复责任

首批托管对象应选择可观察、可恢复的窄任务：PR 审查、CI 归因、候选修复和发布证据包。

本页为实施建议。研发团队的价值重点从代码输入速度转向目标拆解、架构判断、上下文设计、评测和风险处理。自动修改生产数据、不可逆迁移、扩大权限和直接外部发布不适合早期托管。

16 · PRODUCT-TO-ENGINEERING CONTRACT

产品与研发需要
共享工作契约

共同工作契约的目的不是增加文档，而是减少跨团队反复重建上下文。Agent 可以检查契约完整性、寻找冲突和生成执行计划，但不能自行补写未经确认的业务目标、用户承诺或验收标准。

17 · RESPONSIBILITY ARCHITECTURE

组织角色需要围绕
结果责任重新组合

目标与边界

Outcome Owner 定义结果、验收和停止条件。

复用与进化

Workflow Steward 维护工作流、Benchmark 和版本。

运行与治理

Platform、Evaluation 和 Reviewer 分别承担环境、门槛与例外判断。

角色模型属于本文建议。小团队可以一人承担多个角色，但五类责任不能消失。同一个 Agent 不应同时生成、验收并批准自己的结果。人的工作重点将更多集中在目标、证据、例外和外部责任。

18 · MEASUREMENT

衡量标准应转向
可接受结果

NORTH STAR通过验收的工作结果÷人类监督时间
结果

一次验收率 · Lead time · 发布后目标实现

质量

返工 · Revert · 漏报误报 · 生产缺陷

责任

审批队列 · 越权 · 无 Owner 行动 · 升级时延

记忆

来源完整率 · 重复调查 · 结果写回 · 过期状态

Agent 数量、Token 总量和 AI 参与率可以观察，但不能单独证明组织价值。

北极星指标属于本文建议。它要求把人类复核负担纳入价值计算，避免只看到自动化吞吐。随着行动规模扩大，即使单次错误率下降，错误绝对数量和审批压力仍可能增加，因此需要同时观察结果、质量、责任和组织记忆。

19 · 12-MONTH ROADMAP

改造计划从共享语言推进到
可迁移运行

路线图属于实施建议。M0 定义共同状态语言和基线；M1 建立只读可追溯链；M2 允许具名确认后的状态写回；M3 对触发条件影子告警；M4 运行一条受控 Action Loop；M5 检验 Context、Benchmark 和运行记录能否跨模型或 Harness 迁移。

20 · FIRST VERTICAL SLICE

首个试点应打通一条
真实纵向链路

先证明状态链可检查、可纠正、可恢复和可复现，再讨论扩大 Agent 数量与权限。

建议选择一条正在发生、风险可控的真实功能，不建设全公司大图谱。试点需要同时覆盖产品证据、工作契约、研发执行、固定 SHA 验收、人工发布批准和结果写回，由此验证 Context、Harness、Loop 是否真正连接。
