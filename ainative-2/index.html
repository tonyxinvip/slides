05 · THE EVIDENCE CHAIN

真正的产品，是一条证据链

真实问题→价值假设→严谨研究→PRD / 原型→模拟 / 工程→现场使用→数据证据→产品沉淀→市场扩张
同一条事实链 研究定义证据·产品记录过程·市场表达边界·现场反馈回流
市场不是闭环末端，而是证据回流入口；研究也不是上线后负责证明有效的部门。市场主张、产品机制和研究证据必须共享同一条事实链。来源：综合报告第三节。

06 · RESEARCH UPSTREAM

研究不是
“证明部门”，

过程记录什么行为与埋点

研究前置不是增加流程，而是减少无证据开发。研究计划应直接定义字段、行为记录、埋点、评价量表、基线、对照和追踪，最终约束市场主张。来源：综合报告第三节“研究必须进入产品上游”。

模拟只能回答系统是否可能工作，不能替代真实用户、真实行为和真实结果。原型进入生产前必须根据用户规模、数据敏感度和业务责任提高稳定性与治理。来源：综合报告第三节“模拟数据”“工程化边界”。

10 · THREE ENGINEERING LAYERS

Context、Harness、Loop
缺一不可

C

Context

系统知道什么

背景 · 目标 · 业务数据 · 规则 · 历史决策 · 当前状态
H

Harness

系统如何行动并受约束

模型路由 · 数据接口 · 工具 · 权限 · 测试 · 日志 · 回滚
L

Loop

系统如何通过反馈变好

执行 · 检查 · 反思 · 修正 · 验证 · 沉淀 · 再执行

认知基础 + 行动边界 + 进化机制 = 可以承担责任的生产系统。

Context 不是把所有材料一次塞给模型，而是按步骤提供可信、更新的一致信息；Harness 同时提供行动能力和安全边界；Loop 把一次执行变成可评估的持续改进。来源：综合报告第五节。

11 · ORGANIZATION ENGINEERING

新的组织工程，
由五个组件构成

Agent Team生产、研究、审查、测试、发布的角色分工+ Skill把专业方法封装成可复用、可测试的能力+ Workflow定义依赖、检查点、审批与停止条件+ State / Dashboard记录目标、责任、进度、成本、异常与下一步+ Evidence保存结果为何可信、经过什么验证、支持什么结论
Agent Team 解决并行分工，Skill 解决能力复用，Workflow 解决协同顺序，State 解决长周期可见性，Evidence 解决可信度与责任。来源：综合报告第六节。

没有 State，异步会变成失联；没有 Dashboard，管理只能重新回到催问与会议。

State 不是前端看板的数据装饰，而是长任务可以接续、交接、恢复和治理的基础对象。Dashboard 应呈现目标、责任、阶段、成本、证据、异常和人工待办。来源：综合报告第六、七、八节及实施原则“状态先于界面”。

13 · SYSTEM IMPROVEMENT

Dashboard 不追踪工时，
而要支持系统改进

Agent哪些角色贡献结果？

看交付、检查与价值，不评价在线时长

Skill什么值得继续保留？

按调用、成功、边界与复用持续修订

Workflow哪里反复失败？

重写任务拆分、检查点与人工节点

Model成本与影响匹配吗？

高成本低影响的调用必须被替换

可见状态→比较结果→更新 / 停用→再次验证

评价对象是 Agent、Skill、Workflow 与模型配置，不是监控个人工作时长。

Dashboard 的作用不是监控员工，而是记录系统运行：哪些 Agent 参与、调用哪些 Skill、形成什么交付、经过哪些检查、消耗多少资源。依据结果更新或停用系统能力，能够避免 Agent、Skill 和 Workflow 无限堆积。对人的评价仍应基于专业责任、判断与真实结果，而不是在线时长。来源：团队演讲 15:48–16:59；增量报告第五节。

Loop 的目标不是让模型自由改变生产逻辑，而是把错误、用户反馈和评估信号变成受控改进建议，经测试和人工批准后更新 Context、Skill、Workflow 或评估集。来源：综合报告第五节与第十五节。

16 · RESPONSIBILITY, NOT AUTONOMY

AI-native 不是
无人化，
而是重新分工

人负责

目标与最终责任

问题选择 · 教育判断 · 价值取舍 · 关系建立 · 高风险批准

Agent 负责

可规模化执行

搜索 · 生成 · 调用工具 · 检查 · 记录 · 反馈驱动修正

系统负责

判断什么不自动化、什么必须由人决定，本身就是 AI-native 能力。

CocoRobo 不追求“全自动组织”。教育是高信任、高情境、高责任行业。低频、模糊、难验证或缺少稳定输入的任务，可能不适合进入自动循环。来源：综合报告第十五节“需要保持的清醒”。

17 · COLLABORATION MODEL

两类能力，一个
共同证据底座

场景与结果能力理解真实问题设计教育活动进入现场运行验证用户结果
系统与审查能力模型 / Runtime数据 / Workflow研究 / 工程质量隐私 / 安全治理
共同证据底座

目标 · Context · Skill · Workflow 版本 · 评估集 · 运行状态 · 成本 · 真实效果

这不是规定组织架构，而是明确任何团队都需要结果能力、系统能力与专业审查。

这一框架描述的是能力组合，不是组织调整方案。无论采用项目组、产品团队还是跨机构协作，都需要有人理解场景并对结果负责，也需要系统能力和专业审查提供复用与约束；共同证据底座让经验能够跨任务积累。来源：综合报告第八节。

18 · RESPONSIBILITY MODEL

不是定义固定岗位，
而是明确三类责任

结果

对真实结果负责

明确问题、成功标准与最终影响，组织跨专业资源完成闭环。

系统

对运行系统负责

把目标转为 Context、Agent Team、Skill、Workflow、State 与治理规则。

标准

对专业标准负责

建立教育、研究、工程与安全标准，决定结果能否进入真实场景。

责任配置原则一人可以兼任多责→每项责任必须明确，关键判断与批准必须可追溯
三类责任不等于三个固定岗位。小团队可以由一人兼任多项责任，大型项目可以分散给不同专业成员；关键在于任何工作都能回答谁对结果负责、谁维护运行系统、谁守住专业标准。来源：综合报告第八节。

19 · THE NEW PROFESSIONALISM

生产门槛下降，

能力普及写 · 画 · 做 · 开发更快

生产和工程仍然关键，但基础生成门槛下降

→

制作与工程继续重要专业判断决定方向最终责任不能外包

变化不是谁不再重要，而是判断与责任不能被生成能力替代。

这里不是说制作和工程不再重要。生成能力改变的是能力配置：基础生产更快，工程仍决定可靠性，而问题定义、专业审查、价值取舍和最终责任的权重继续上升。来源：团队演讲 23:48–28:47；增量报告第六节。

23 · RELATIONSHIP CONTEXT

真正的个性化，不是多生成一份内容，而是理解“这个人此刻为什么需要它”。

28 · THE WORKFLOW CONTRACT

没有最小合同，Workflow
只是自动化串联

01目标

要改变什么结果

02输入

可信来源与适用边界

03负责人

谁对最终结果负责

04状态

阶段、阻塞与下一步

05工具与权限

能读、能写、能执行什么

06检查点

何时评估、审批或停止

07输出

交付对象与质量标准

08证据

依据、测试与验证记录

09回流

如何进入下一轮改进

一条 Workflow 的价值，不在步骤更多，而在责任、状态、判断与证据都被明确。

所有工作流都应具备输入、目标、状态、负责人、工具、检查点、输出、证据和回流机制。这份最小合同让不同部门能够共享同一种组织语言。来源：综合报告第十节末尾与实施原则。

29 · SCHOOL CAPABILITIES

学校需要补齐五种系统能力

数据治理

连接教学、学习、内容与评价数据，保持身份、语义、权限和用途一致。

能力编排

根据任务选择模型、工具、流程与人工节点。

效果验证

让教学过程、产品效果与学习结果形成可追溯证据。

安全治理

管理权限、隐私、安全、成本、审计与模型变化。

现场共创

与教师共同调试流程、修正 Skill，并把经验沉淀为可复制方法。

单个工具可以快速采购；把工具变成可持续教育系统，需要这五种能力共同成立。

这是学校侧的能力缺口框架，不是供应商销售目录。不同机构可以自行建设、与伙伴共建或采购服务；关键是数据、编排、验证、治理与现场共创必须共同成立。来源：综合报告第十一节。

30 · PLAUSIBLE DRIFT

AI 系统最危险的，
是“看起来完成”

V1.0 任务规范目标与验收→长周期执行并行与自我修正→自称完成局部合理，整体偏航→漂移审计逐条对照规范→人类批准 / 回滚版本化进入下一轮
验收标准可执行阶段检查不只看终点交付必须带证据状态、权限与成本可追溯保留旧版本与接管入口

管理 Agent，就是不断缩小“自称完成”与“可证实完成”之间的距离。

演讲提出一种比明显报错更难发现的风险：长任务执行中，Agent 可能逐渐偏离初始规范，却产出局部合理、形式完整的“完成结果”。治理因此不能只看最终输出，还要保留任务规范、阶段状态、证据、成本与版本。模型仍应按复杂度和风险分层；确定性规则优先，轻量模型承担高频低风险任务，高能力模型用于关键推理与审查。来源：团队演讲 27:04–27:52；增量报告第四节。

32 · THE NEXT 90 DAYS

任何机构都可以用 90 天，
验证一条真实闭环

01—30

选一条真实任务

先定义验收
31—60

跑通两轮真实使用

这是一套任何学校或机构都可以采用的试点方法，而不是 CocoRobo 的内部路线图。先选真实任务、跑两轮使用、记录证据，再抽象已验证能力，避免平台先行。来源：增量报告第十二节；综合报告实施原则。

33 · PILOT METHOD

不要从“大平台”开始，
从一个可验证试点开始

真实高频

教师与学生每周都会发生，不依赖演示场景

跨越形态

同一目标需要课件、互动、Tutor 或项目工具协同

状态回流

每次行动都能更新目标、过程、作品与下一步

责任明确

结果、系统与专业标准都有人承担

教师负担状态连续率真实采用人工接管率证据完整度单位成本

世界变了：应用会越来越容易生成，真正稀缺的是持续理解教育现场、保留长期状态、作出专业判断，并对结果负责。

带走的方法

选择一项真实高频任务，记录基线，用 90 天验证连续状态、真实采用、证据与成本。

结尾给出可迁移的方法：选择一项真实、高频、能够持续回写状态的任务，记录现状基线并明确责任。90 天后用真实采用、状态连续、证据完整、用户负担和成本判断是否值得扩大。
