05 · THE EVIDENCE CHAIN

真正的产品，是一条证据链

真实问题→价值假设→严谨研究→PRD / 原型→模拟 / 工程→现场使用→数据证据→产品沉淀→市场扩张
同一条事实链 研究定义证据·产品记录过程·市场表达边界·现场反馈回流
市场不是闭环末端，而是证据回流入口；研究也不是上线后负责证明有效的部门。市场主张、产品机制和研究证据必须共享同一条事实链。来源：综合报告第三节。

研究前置不是增加流程，而是减少无证据开发。研究计划应直接定义字段、行为记录、埋点、评价量表、基线、对照和追踪，最终约束市场主张。来源：综合报告第三节“研究必须进入产品上游”。

07 · SIMULATION, ENGINEERING, REALITY

工程强度由风险、规模与责任决定；快速原型不等于绕过工程质量。

模拟只能回答系统是否可能工作，不能替代真实用户、真实行为和真实结果。原型进入生产前必须根据用户规模、数据敏感度和业务责任提高稳定性与治理。来源：综合报告第三节“模拟数据”“工程化边界”。

10 · THREE ENGINEERING LAYERS

Context、Harness、Loop
缺一不可

C

Context

系统知道什么

背景 · 目标 · 业务数据 · 规则 · 历史决策 · 当前状态
H

Harness

系统如何行动并受约束

模型路由 · 数据接口 · 工具 · 权限 · 测试 · 日志 · 回滚
L

Loop

系统如何通过反馈变好

执行 · 检查 · 反思 · 修正 · 验证 · 沉淀 · 再执行

认知基础 + 行动边界 + 进化机制 = 可以承担责任的生产系统。

Context 不是把所有材料一次塞给模型，而是按步骤提供可信、更新的一致信息；Harness 同时提供行动能力和安全边界；Loop 把一次执行变成可评估的持续改进。来源：综合报告第五节。

11 · ORGANIZATION ENGINEERING

新的组织工程，
由五个组件构成

Agent Team生产、研究、审查、测试、发布的角色分工+ Skill把专业方法封装成可复用、可测试的能力+ Workflow定义依赖、检查点、审批与停止条件+ State / Dashboard记录目标、责任、进度、成本、异常与下一步+ Evidence保存结果为何可信、经过什么验证、支持什么结论
Agent Team 解决并行分工，Skill 解决能力复用，Workflow 解决协同顺序，State 解决长周期可见性，Evidence 解决可信度与责任。来源：综合报告第六节。

没有 State，异步会变成失联；没有 Dashboard，管理只能重新回到催问与会议。

State 不是前端看板的数据装饰，而是长任务可以接续、交接、恢复和治理的基础对象。Dashboard 应呈现目标、责任、阶段、成本、证据、异常和人工待办。来源：综合报告第六、七、八节及实施原则“状态先于界面”。

8月17日实践把 Dashboard 的含义推进了一层：它记录哪些 Agent 工作、调用哪些 Skill、形成什么交付、消耗多少资源，进而支持角色降级、Skill 删除和 Workflow 重写。Agent Team 应被视为动态队伍，而不是固定组织图。来源：团队演讲 15:48–16:59；增量报告第五节。

16 · RESPONSIBILITY, NOT AUTONOMY

AI-native 不是
无人化，

人负责

Agent 负责

可规模化执行

系统负责

判断什么不自动化、什么必须由人决定，本身就是 AI-native 能力。

CocoRobo 不追求“全自动组织”。教育是高信任、高情境、高责任行业。低频、模糊、难验证或缺少稳定输入的任务，可能不适合进入自动循环。来源：综合报告第十五节“需要保持的清醒”。

18 · ROLES & MANAGEMENT

三类角色，重新定义责任

结果

闭环负责人

对一个真实用户问题或业务结果负责，跨研究、产品、交付与验证组织资源。

系统

Agent 系统设计者

把目标转为 Context、Agent Team、Skill、Workflow、State 与治理规则。

标准

专业审查者

建立教育、研究、工程、品牌与安全标准，决定结果能否进入真实场景。

管理也要变化从催进度与人工同步→管理目标、优先级、预算、状态、约束与验收
一个人可以兼任两种角色，但三类责任必须明确：谁负责结果、谁负责系统、谁负责专业判断。会议应更多用于决策、冲突解决与复盘，而不是人工同步全部事实。来源：综合报告第八节。

人人都能生成应用，不等于人人都能做专业产品。

生成能力降低制作门槛，却放大检查、修正、伦理判断、体验打磨和责任承担。未来通用协调型角色会被压缩，拥有专业标准、管理经验并能组织 AI 系统的人更重要。公司不要求所有人都成为全栈工程师，而要把系统能力平台化。来源：团队演讲 23:48–28:47；增量报告第六节。

23 · RELATIONSHIP CONTEXT

28 · THE WORKFLOW CONTRACT

没有最小合同，Workflow
只是自动化串联

01目标

要改变什么结果

02输入

可信来源与适用边界

03负责人

谁对最终结果负责

04状态

阶段、阻塞与下一步

05工具与权限

能读、能写、能执行什么

06检查点

何时评估、审批或停止

07输出

交付对象与质量标准

08证据

依据、测试与验证记录

09回流

如何进入下一轮改进

一条 Workflow 的价值，不在步骤更多，而在责任、状态、判断与证据都被明确。

所有工作流都应具备输入、目标、状态、负责人、工具、检查点、输出、证据和回流机制。这份最小合同让不同部门能够共享同一种组织语言。来源：综合报告第十节末尾与实施原则。

30 · PLAUSIBLE DRIFT

AI 系统最危险的，
是“看起来完成”

V1.0 任务规范目标与验收→长周期执行并行与自我修正→自称完成局部合理，整体偏航→漂移审计逐条对照规范→人类批准 / 回滚版本化进入下一轮
验收标准可执行阶段检查不只看终点交付必须带证据状态、权限与成本可追溯保留旧版本与接管入口

管理 Agent，就是不断缩小“自称完成”与“可证实完成”之间的距离。

演讲提出一种比明显报错更难发现的风险：长任务执行中，Agent 可能逐渐偏离初始规范，却产出局部合理、形式完整的“完成结果”。治理因此不能只看最终输出，还要保留任务规范、阶段状态、证据、成本与版本。模型仍应按复杂度和风险分层；确定性规则优先，轻量模型承担高频低风险任务，高能力模型用于关键推理与审查。来源：团队演讲 27:04–27:52；增量报告第四节。

可替换，不绑定核心状态

数据主权原则谁能看、谁能调用、什么可以外发、何时删除，都必须成为系统状态。

这是待验证的架构假设，不是已成立的采购或部署结论。

学校既需要外部模型快速演进的能力，也需要对身份、学生数据、长期状态和教育证据保持控制。更可能的路径是本地或区域持有核心状态，通过受控网关调用外部能力。具体部署形态必须根据法规、成本、学校能力和试点证据验证。来源：团队演讲 58:10–58:59；增量报告第八节。

32 · THE NEXT 90 DAYS

未来 90 天，只证明一件事：
应用可变，状态不丢

01—30

不先建平台
31—60

用两种应用形态跑通

让同一任务跨课件 / Tutor / H5 继续运行，并加入漂移检查与人工接管。

状态连续，证据回流
61—90

只抽象最小底座

沉淀必要的状态对象、能力接口、权限、证据与部署类型。

被真实使用后再平台化

最低成功标准：真实教师采用，应用可以替换，教育状态可以接续，关键结论有证据。

新版本把原先“三条 Workflow”收缩为一条最小但完整的教育闭环。原因是新判断需要先证明核心命题：应用形式变化时，身份、目标、过程、作品、评价和证据能否保持连续。通过真实使用再抽象底座，避免平台先行。来源：增量报告第十二节；综合报告实施原则。

33 · THE DECISION

下一步，不是建“大平台”
而是选出一条教育闭环

真实高频

教师与学生每周都会发生，不依赖演示场景

跨越形态

同一目标需要课件、互动、Tutor 或项目工具协同

状态回流

每次行动都能更新目标、过程、作品与下一步

有人负责

闭环负责人、专业审查者和试点学校明确

教师负担状态连续率真实采用人工接管率证据完整度单位成本

世界变了：应用会越来越容易生成，真正稀缺的是持续理解教育现场、保留长期状态、作出专业判断，并对结果负责。

现在的决定

确定任务、负责人、专业审查者与试点学校；用 90 天证明这一条闭环。

结尾收敛为一个可执行决定：选一条真实、高频、跨应用形态、能够持续回写状态的教育任务，明确闭环负责人、专业审查者和试点学校。90 天之后，我们用真实采用、状态连续、证据完整、教师负担和成本判断是否值得扩大。
