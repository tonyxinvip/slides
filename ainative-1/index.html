01 · THREE QUESTIONS

同样是大模型，
为什么今天的 Agent 更像在工作？

2023为什么 AutoGPT 看起来很忙，事情却经常做不完？
2024—2025为什么最先跑通的，偏偏是写代码的 Agent？
今天为什么大家开始谈工作环境，而不只谈模型？

沿着这三个问题回看历史，会发现变化发生在模型周围。

2023 年，AutoGPT 会自己列任务、不断往下跑，但常常越跑越偏。两年以后，Coding Agent 已经能接下一整件工程任务。模型当然变强了，可只用“模型升级”解释不完这段变化。接下来我想沿着三个问题，把真正改变的部分找出来。

03 · 17 DEC 2021 · WEBGPT

研究者给 GPT-3 做了一个
只有文字命令的浏览器

模型边浏览边收集引用；人类因此可以顺着证据检查它有没有说错。

这一步很小，却第一次把“找资料”和“留下证据”放进同一条工作链。

研究者没有让 WebGPT 直接操作完整浏览器，而是把搜索、打开页面、翻页等动作变成文字命令。模型浏览时还必须收集引用，方便人类沿着证据检查。论文由 Reiichiro Nakano 领衔，2021 年 12 月 17 日提交。后来 Agent 常见的环境、动作、观察和证据，在这里已经能看到雏形。

07 · THE RELIABILITY WALL

每一步只错一点，
走三十步也可能完全跑偏

0.9530≈ 21%

只作风险示意：假设每一步都有 95% 的把握，而且彼此独立，连续 30 步全部做对的机会也只剩约 21%。现实中，前一步的错还会带偏后一步。

理解错目标选错工具记错进度不会恢复不知何时停

让 Agent 循环起来并不难；难的是每一步都有检查，出错能退回，危险时会停手。

这个公式不是任何产品的实测，只是一个风险示意。它想说明一件很朴素的事：单步看起来很准，不代表三十步以后还在正确方向。AutoGPT 时代最直观的问题就是，系统一直很忙，却可能把一个小错误越滚越大。所以长任务一定要有检查点、重试、回滚，也要能交还给人。

10 · THE MULTI-AGENT LESSON

多放几个 Agent，
不会自动变成好团队

只有角色名

大家都在转述

每个 Agent 都说一点相似的话，交接越多，信息损失和错误传播越严重。

有不同责任

每一棒都有凭据

资料、权限、工具、产物或验收责任不同，分工才可能带来额外价值。

最后能留下来的，是清楚的交接规则和可以检查的中间产物。

我自己的判断是，多 Agent 最容易做成角色扮演：给几个相似模型贴上不同职位，再让它们反复讨论。名字不同，不等于责任不同。只有资料、权限、工具、产物或者验收责任真的分开，多个 Agent 才可能比一个 Agent 更有价值。
11 · WHY CODING FIRST

代码世界为什么最早跑通？
做错了会立刻报错

写代码→编译→测试→读错误→修复↺
结果容易判断

编译器、测试、lint、CI 会直接暴露失败。

过程留有痕迹

文件、差异、提交和日志都可以复查。

出错能够退回

沙箱、分支和回滚把影响限制在小范围。

Coding Agent 领先，不只因为模型会写代码，更因为它身边有一整套现成的检查工具。

为什么最先跑通的是代码？文章写得好不好，很难让机器当场判断；代码能不能编译、测试能不能通过，结果马上就出来。Agent 可以读回错误，再修下一轮；文件、diff 和 commit 又把每次动作都留下来。代码世界早就准备好了一套能行动、能检查、能退回的环境。

22 · PRODUCT EVOLUTION

产品每往前一步，
人就多交出一层执行责任

01聊天机器人回答问题
02副驾驶给出建议
03IDE Agent编辑 + 终端
04终端 Agent连续完成
05云端 Agent远程 + 并行
06AI Worker接下目标

从“告诉我答案”到“把事情做完”，中间多出来的是上下文、行动、检查和责任。

这六层不是严格的产品分类，一个产品可能同时站在几层。我要强调的是，产品每往前一步，人就多交出一层责任：先是答案，再是建议、编辑、连续执行、远程并行，最后是一个完整目标。判断它走到哪一层，要看系统替人承担了多少组织、行动、检查和持续运行。

同一个模型，上午能干活，
下午也可能闯祸

第一步拿到旧版制度文件

它引用了已经失效的规则。

→
第二步拥有直接发送权限

错误内容没有经过复核。

→
第三步失败后继续重试

一次错误变成多次错误。

模型没有换换掉的是它看到的资料、能做的动作，以及什么时候停。

这是示意案例，不指向某个产品；它说明为什么“模型够强”仍不等于“可以放心委派”。

设想一个很普通的任务：让 Agent 按公司制度回复客户。上午它拿到最新版文件，只能生成草稿，发出前还要人确认；下午它读到旧版制度，却获得了直接发送权限，失败以后还不断重试。同一个模型，结果可以完全不同。问题不在一句提示词，而在它开工时看到了什么、能做什么、什么时候必须停。
24 · CONTEXT ENGINEERING · SYSTEMATIZED 2025

Context Engineering：
先把工作桌面收拾对

任务目标工作说明参考范例可信资料眼前这张桌长期记忆当前进度历史记录用户意图
资料太少，会瞎猜·资料太多，也会找错重点

该看的及时出现，不该看的暂时收起；来源、版本和当前进度都要说清楚。

工程文章Anthropic · 29 Sep 2025
先看刚才案例的第一步：Agent 为什么读到了旧制度？Context Engineering 管的就是这张开工桌面。任务、规则、范例、可信资料和当前进度，哪些应该摆在眼前，哪些应该暂时收起来。资料不是越多越好；版本错了、重点埋了，同样会误导判断。
25 · HARNESS ENGINEERING · NAMED 2026

Harness Engineering：
工具要好用，门也不能乱开

工具

每个动作说得清楚

运行环境

先在隔离空间里做

门禁

越重要的动作，越要审批

反馈

结果和错误都能读懂

验收

别让它自己给自己打分

恢复

做错了能退回上一步

刚才案例里的直接发送权限，就是工作间的门开得太大。

工程文章OpenAI · 11 Feb 2026
再看第二步：为什么一条错误回复能直接发出去？Harness 管的是行动环境。Agent 有哪些工具，在哪运行，能进哪些门，做完以后看到什么反馈，谁来验收，出错怎样退回。权限不是越多越先进；越接近真实世界，越要把高风险动作单独拦住。
26 · LOOP ENGINEERING · AN EMERGING LABEL

Loop Engineering：
每跑一轮，都要问还该不该继续

目标计划行动看结果检查总结重试停止 / 叫人
做对了吗预算够吗还要试几次需要审批吗异常交给谁经验写到哪里

没有停止条件，重试不会自动变成改进，只会把同一个错误再做一遍。

方法前史ReAct · 2022Reflexion · 2023
最后看第三步：为什么失败以后还在继续发？Loop 管的不是“让它永远运行”，而是每一轮都检查结果。做对了吗，预算还够吗，还能试几次，这一步需不需要审批，异常交给谁。Loop Engineering 还是一个正在形成的说法，但这些实践从 ReAct、Reflexion 到今天的生产系统一直都在。
27 · THE WORK AROUND THE MODEL

只比较模型，
已经解释不了结果差距

边界
何时停
怎么做
看什么
模型

Context 决定它看什么；Harness 决定它能做什么；Loop 决定下一步继续、重试还是叫人。

更难复制的，是资料、工具、验证和责任怎样接在一起。
同样的模型放进不同工作环境，结果会完全不同。Context 管它看什么，Harness 管它能做什么，Loop 管下一步怎么办，权限、预算和审计把三者围起来。模型仍然重要，但只比较模型，已经解释不了一家公司、一所学校最后拿到的结果。这是我根据前面历史做出的判断。
28 · THE HUMAN JOB

人不必一直守着 Agent，
但要守住三个关口

派工前

把任务说清楚

为什么做、先做什么、哪些地方不能碰。

进行中

只盯关键节点

高风险动作、预算变化和异常情况必须叫人。

交付时

看证据，不看语气

检查来源、测试、修改记录和没有解决的问题。

人省下的是守在屏幕前的时间；省不掉的是判断和责任。

远程、异步、并行以后，人当然不必一直守着屏幕。但工作没有凭空消失，它移到了三个关口：派工前把目标和禁区说清楚；进行中只盯高风险节点；交付时看来源、测试和修改记录。Agent 可以承担执行，人仍然要承担判断和结果责任。
29 · VERDICT & HANDOFF

AI Worker 能接下一件事，
做不下去时也会停下来叫人

看对资料→用对工具→交出证据
权限不够 · 预算超限 · 结果存疑 → 停止并升级

三十年的技术接力，不只让模型更聪明，也给它配上了工作桌、工具、检查和边界。
